# Presentations: Organizer/Reviewer ดูเฉพาะไฟล์ฉบับล่าสุด

วันที่: 2026-10-27 (Asia/Bangkok)

สถานะ: ผู้ใช้ตรวจทานและอนุมัติ spec ในแชตแล้ว และอนุมัติให้จัดทำ implementation plan ยังไม่เริ่มแก้โค้ด

## เป้าหมาย

เปิดหน้า Backoffice `/presentations` และ `/presentations/:abstractId` ให้ role `organizer` และ `reviewer` ใช้ดูเฉพาะไฟล์นำเสนอฉบับล่าสุดที่รับสำเร็จ ตาม Event และประเภทงานที่ได้รับสิทธิ์เดิม โดยไม่เห็นคำขอแก้ไข ประวัติอีเมล ประวัติการดำเนินการ หรือข้อมูลตรวจสอบภายใน ทั้งในหน้าเว็บและ response ของ API

Admin ยังคงเห็นไฟล์ทุกฉบับ ประวัติ และใช้การจัดการทั้งหมดได้ตามเดิม

## บริบทจากโค้ดปัจจุบัน

- Backoffice บล็อกสอง role นี้ผ่านรายการสิทธิ์หน้า เมนู และตัวตรวจสิทธิ์ในหน้ารายการ/รายละเอียด ปัจจุบันหน้าดังกล่าวใช้ `readable = isAdmin`
- API `requirePresentationStaff()` ตรวจผู้ใช้ที่ active, role/email ปัจจุบัน, PRIS-2026 Event, `staff_event_assignments` และ `assigned_presentation_types` จากฐานข้อมูลอยู่แล้ว
- Reader ของ API กรอง Organizer/Reviewer ให้เห็นเฉพาะงานที่มี `currentUpload` และประเภทที่ได้รับสิทธิ์ก่อนแบ่งหน้าอยู่แล้ว
- API ซ่อนข้อมูลอีเมลและผลตรวจบางส่วนแล้ว แต่ยังส่ง `requests`, revision audit, `activeRequest`, สถานะการแก้ไข และไฟล์ทุกฉบับให้สอง role นี้
- หน้ารายการมีตัวนับ/ตัวกรองสถานะการแก้ไข หน้ารายละเอียดมีไฟล์เก่า คำขอแก้ไข และลิงก์เชื่อมไฟล์กับคำขอ จึงต้องปรับทั้ง UI และข้อมูลที่ API ส่ง

## ทางเลือกและข้อสรุป

1. **ปรับหน้าและ API เดิมตาม role (เลือก):** ใช้ระบบสิทธิ์และเส้นทางเดิม เพิ่ม projection สำหรับผู้ดูไฟล์และเงื่อนไขแสดง UI ใช้ส่วนแสดงผลงาน/ไฟล์ร่วมกันได้และไม่เพิ่ม endpoint
2. **แยกหน้าและ API สำหรับดูไฟล์:** สัญญาข้อมูลแยกจากงานจัดการชัดเจน แต่เพิ่มเส้นทางและส่วนแสดงผลที่ต้องดูแล ยังไม่จำเป็นสำหรับขอบเขตนี้

การซ่อนเฉพาะ UI ไม่เพียงพอ ต้องจำกัดข้อมูลใน response ของ API ด้วย

## สิทธิ์และขอบเขตข้อมูล

| ผู้ใช้ | รายการที่เห็น | รายละเอียด | การจัดการ |
| --- | --- | --- | --- |
| Admin | ตามพฤติกรรมเดิม รวมงานที่ยังไม่ส่ง | ทุกฉบับและประวัติเดิม | ตามเดิม |
| Organizer/Reviewer | มีไฟล์ที่รับสำเร็จ และตรง Event/ประเภทที่ได้รับสิทธิ์ | ข้อมูลผลงาน ผู้ส่ง และไฟล์ปัจจุบันเพียงฉบับเดียว | ไม่มี |
| Role อื่น | ไม่เปิดสิทธิ์เพิ่ม | ไม่เปิดสิทธิ์เพิ่ม | ไม่เปิดสิทธิ์เพิ่ม |

- คงกติกาประเภทเดิม: สิทธิ์ `poster` ครอบคลุม Highlighted Poster; ไม่ได้กำหนดประเภทให้เห็นรายการว่าง
- คงขอบเขตจาก Event และประเภทเดิม ไม่เพิ่มเงื่อนไขหมวด Abstract ของ Reviewer ในงานนี้
- ใช้ `presentation_targets.current_upload_id` เป็นแหล่งอ้างอิงไฟล์ล่าสุดที่รับสำเร็จ ไม่เลือกจาก upload attempt หรือเรียงวันที่เอง
- คำขอแก้ไขที่เปิดอยู่ หมดเวลา หรือยกเลิก ไม่ทำให้ไฟล์ปัจจุบันหายไป ระหว่างอัปโหลดฉบับใหม่ยังแสดงฉบับที่รับสำเร็จเดิม
- รายละเอียดงานที่ยังไม่มีไฟล์หรืออยู่นอกขอบเขต Event/ประเภทของผู้ดูตอบ 404 ตาม reader เดิม การขาดสิทธิ์ Event หรือ session ใช้ข้อผิดพลาดเดิม
- งานที่ถูกถอนจากประกาศแต่ยังเข้าเงื่อนไข reader เดิมคงพฤติกรรมเดิม ไม่เปลี่ยนกติกา roster ในงานนี้

## หน้าเว็บสำหรับ Organizer/Reviewer

### เมนูและหน้ารายการ

- เปิดเมนู Presentations รวมถึงเข้าผ่าน URL โดยตรงได้ ใช้การตรวจสิทธิ์หน้าร่วมกับ AuthGuard เดิม
- มีมุมมองไฟล์นำเสนอที่ได้รับเท่านั้น แสดง Tracking ID, ชื่อผลงาน, ชื่อและอีเมลผู้ส่ง, ประเภท/หมวด, Round, กลุ่มผลงานทั่วไป/นักศึกษา, วันที่รับ และลิงก์ไฟล์ปัจจุบัน
- คงค้นหา การเลือก Event ภายในสิทธิ์ การกรอง Round/ประเภท/กลุ่มผลงาน และ pagination
- ไม่แสดงตัวกรองสถานะการแก้ไข ตัวนับรอแก้ไข/แก้ไขแล้ว สถานะคำขอ วันปิดรับคำขอ หรือผลตรวจ/อีเมล แสดงจำนวนงานที่ได้รับตามตัวกรองได้
- ไม่แสดงปุ่มตรวจรายชื่อ ตั้งกำหนดส่ง รับรอง ส่งอีเมล เลือกส่งหลายงาน หรือปุ่มจัดการอื่น

### หน้ารายละเอียด

- แสดงข้อมูลผลงานและผู้ส่ง พร้อมไฟล์ปัจจุบันเพียงหนึ่งรายการ ชื่อไฟล์ เวอร์ชัน ขนาด และวันที่รับแสดงได้
- Oral เปิดด้วยลิงก์ Google Drive; Poster/Highlighted Poster ใช้วิธีเปิดไฟล์ตามชนิดไฟล์เดิม โดยเคารพ `fileStatus` และ nullable `fileUrl`
- ไม่มีส่วนไฟล์ทุกฉบับ ประวัติไฟล์ถูกลบ คำขอแก้ไข ประวัติอีเมล audit ผลตรวจ/รับรอง หรือ dialog จัดการ
- ไม่มีข้อความแจ้งคำขอที่เปิดอยู่ ลิงก์ไปคำขอ หรือป้ายรอแก้ไข/แก้ไขแล้ว แม้เคยรับไฟล์จากคำขอแก้ไข
- เมื่อไม่มี URL ที่ใช้งานได้ แสดงข้อความว่าเปิดไฟล์ไม่ได้ โดยไม่ย้อนกลับไปใช้ไฟล์เก่า
- เมื่อเปลี่ยนผู้ใช้ role token หรือ Event ต้องไม่แสดงข้อมูลจาก scope เดิมระหว่างโหลด

## API และการไหลของข้อมูล

ใช้ GET list/detail เดิม ตรวจสิทธิ์ด้วยฐานข้อมูลก่อนอ่านข้อมูลตาม scope แล้วสร้าง projection สำหรับผู้ดูไฟล์ ส่วน Admin ใช้ข้อมูลและ workflow เดิม

### Projection สำหรับผู้ดูไฟล์

- อนุญาตข้อมูลผลงาน ผู้ส่ง และ `currentUpload` ที่ใช้แสดงหน้าตามข้างต้น
- `uploads` ในรายละเอียดมีเฉพาะ `currentUpload` หนึ่งฉบับ ไม่อ่านหรือส่งไฟล์เก่าเพื่อแสดงให้ผู้ดู
- `requests`, `emailJobs` และ `audit` เป็นอาร์เรย์ว่าง; `activeRequest` และ `lastEmail` เป็น null; `canNotify` และ `capabilities.manage` เป็น false
- `revisionRequestId` ของไฟล์ที่ส่งให้ผู้ดูเป็น null ทั้งในรายการและรายละเอียด เพื่อไม่เผยตัวเชื่อมไปคำขอ
- คงการปิดบัง `matchState`, fingerprint, snapshot, problems, ผู้รับรอง เวลาและเหตุผลรับรอง ด้วยค่า null/ว่างตาม DTO เดิม
- สถานะสำหรับผู้ดูเป็น `submitted` หมายถึงมีไฟล์ที่รับสำเร็จ ไม่เผยว่ากำลังขอแก้ไข แก้ไขแล้ว หรือหมดเวลาแก้ไข
- ตัวนับสำหรับผู้ดูคำนวณจากข้อมูลที่ผ่าน scope และตัวกรองที่อนุญาตแล้ว โดยนับทั้งหมดเป็น `submitted`; ตัวนับสถานะอื่นเป็นศูนย์ ไม่เปลี่ยนตัวนับของ Admin
- พารามิเตอร์ `status` และ `matchState` ที่ผ่าน schema แล้วไม่มีผลต่อผลลัพธ์ของผู้ดู แม้เรียก API เอง เพื่อไม่ให้อนุมานสถานะภายในผ่านจำนวนรายการ ผู้ดูเห็นเฉพาะงานที่มีไฟล์เสมอไม่ว่าจะส่ง `received` หรือไม่
- ไม่เพิ่มข้อมูล workflow หรือประวัติใหม่ใน settings response; หน้า Viewer ไม่เรียก endpoint settings/history ที่สงวนไว้ให้ Admin
- ไม่ query รายละเอียดคำขอ ประวัติอีเมล หรือ audit เพื่อส่งในรายละเอียดของผู้ดู หาก reader กลางต้องใช้ข้อมูล workflow เพื่อคำนวณค่าภายใน ต้องปิดบังก่อนส่ง response และก่อนนำไปกรอง/นับสำหรับผู้ดู

สิทธิ์เขียนทั้งหมด เช่น ขอ/ยกเลิกแก้ไข ตั้งกำหนดส่ง ตรวจรายชื่อ รับรอง ส่ง/ส่งซ้ำอีเมล และอ่าน notification batch/settings history ยังคงเป็น Admin เท่านั้น

## ขอบเขตไฟล์และโครงสร้าง

- `conference-api/src/modules/presentations/readers.ts`: จำกัด projection ของ list/detail และตัวกรอง/ตัวนับสำหรับผู้ดู โดยคง `requirePresentationStaff()` เป็นแหล่งตรวจสิทธิ์
- `conference-backoffice/src/contexts/AuthContext.tsx` และ `src/components/layout/Sidebar.tsx`: เปิดสิทธิ์หน้าและเมนูให้สอง role; ใช้ AuthGuard เดิม ไม่เปลี่ยนสิทธิ์หน้าอื่น
- `conference-backoffice/src/app/presentations/page.tsx`, `[abstractId]/page.tsx` และ `src/components/presentations/PresentationTable.tsx`: เปิดหน้าและจำกัดส่วนแสดงตาม role ทั้งโหมดรายการและรายละเอียด
- ปรับ DTO types/helpers ที่เกี่ยวข้องเท่าที่จำเป็น และคง contract ของ Admin ไม่ต้องแยก service หรือ framework สิทธิ์ใหม่
- ใช้ชุดทดสอบ presentation readers/routes และ Backoffice presentation UI ที่มีอยู่ เพิ่มกรณีตามพฤติกรรมที่เปลี่ยน

ไม่แก้ฐานข้อมูล ไม่เพิ่ม migration/dependency/endpoint ไม่เปลี่ยนการรับไฟล์ storage worker email หรือหน้าเจ้าของผลงานใน Pris2026 ขอบเขตนี้แทนที่พฤติกรรมเดิมที่ให้ Organizer/Reviewer อ่าน revision history และไฟล์เก่าใน Backoffice

## การตรวจรับ

1. ทดสอบ Organizer และ Reviewer แยกกัน: เข้าเมนู/หน้ารายการ/หน้ารายละเอียดได้เฉพาะ Event และประเภทที่มีสิทธิ์ ไม่มีประเภทแสดงว่าง และ role อื่นไม่ได้สิทธิ์เพิ่ม
2. เตรียมงานที่มีไฟล์เก่า ไฟล์ล่าสุด คำขอเปิด/ยกเลิก/หมดเวลา อีเมล และ audit: API list/detail ส่งเฉพาะไฟล์ปัจจุบัน ไม่มีข้อมูลคำขอ/ประวัติหรือตัวเชื่อมคำขอ และ UI ไม่แสดงส่วนเหล่านั้น
3. ตรวจไฟล์ปัจจุบันทั้ง Oral, Poster และ Highlighted Poster รวมไฟล์ที่ไม่มี URL/เปิดไม่ได้; ไม่มีการเผยลิงก์เก่าทดแทน
4. ตรวจ scope ก่อน pagination/total/counts และลองใส่ `status`, `matchState`, เปลี่ยน `received` โดยตรง: ไม่ทำให้เห็นงานนอกสิทธิ์หรือนับ/กรองจาก workflow ภายใน
5. ตรวจค้นหา Round/ประเภท/กลุ่มผลงาน และการเปลี่ยน session/Event ว่าไม่แสดงข้อมูลเก่าระหว่างโหลด
6. ตรวจการเปิดรายละเอียดงานไม่มีไฟล์/นอกประเภทเป็น 404 และ API จัดการ/ประวัติที่สงวนไว้ยังตอบ 403 สำหรับทั้งสอง role
7. ตรวจ Admin ยังคงมี roster สถานะ ตัวกรอง counts ไฟล์ทุกฉบับ ประวัติ และปุ่มจัดการตามเดิม รวมงานที่ยังไม่ส่ง
8. รันชุดทดสอบที่เกี่ยวข้องของ API และ Backoffice พร้อม type/build/lint checks ที่เหมาะสม บันทึกข้อจำกัดของ integration environment หากรันไม่ได้

## การส่งมอบ

จัดทำ implementation plan หลังผู้ใช้ตรวจเอกสารนี้แล้ว ปรับ API และ Backoffice เป็นชุดที่สอดคล้องกัน โดยตรวจ contract และการปิดบังข้อมูลทั้งสองฝั่งก่อนส่งมอบ
